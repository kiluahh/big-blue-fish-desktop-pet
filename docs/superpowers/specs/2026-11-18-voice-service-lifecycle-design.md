# 语音服务生命周期设计

## 问题

`2026-11-18-speech-tts-design.md` 里语音服务是使用者自己开的常驻进程，程序只按 `SpeechEndpoint` 去连。结果是：

- 宠物退出后，`python` 服务仍在跑。实测三个服务合计约 10 GB 物理内存、19 GB 提交、2.2 GB 显存。
- venv 里的 `python.exe` 只是壳，真解释器是它的子进程；只杀壳进程，模型照样占着内存和显存。
- 每次想用语音都得先开一个黑窗；忘了开就静默没声音。

## 目标

语音服务由程序托管：需要时启动，宠物退出时连同子进程一起收走，显存和内存随之释放。外部已经在跑的服务保持现状——只连接、不杀。

## 行为

1. 启动后后台检查：语言总开关打开、引擎不是「系统语音」、接口地址是本机（`127.0.0.1` / `localhost` / `::1`）、当前没有服务应答 → 在语音文件夹里拉起对应脚本。已经应答则记为「外部服务」，退出时不动。
2. 引擎切换、改接口地址、语音页的「检测服务」「试听」、重新打开语音开关都走同一条保证路径（已启动则跳过，幂等）。
3. 关掉语音总开关，或把引擎切成系统语音，就停止程序自己拉起的那份服务。
4. 退出时 `Kill(entireProcessTree: true)`，最多等 3 秒，写一条诊断，再走 `Application.Shutdown()`。
5. 启动失败（找不到 python、进程秒退、60 秒未就绪）只写诊断并在设置页显示原因；气泡照常出字，不弹窗。

## 组成

| 部分 | 位置 | 职责 |
| --- | --- | --- |
| `VoiceServicePlan` | `Companion/CompanionVoiceService.cs` | 纯函数：引擎→脚本名与端口、本机判定、解释器解析、命令行拼装；不启动进程，可单独测 |
| `CompanionVoiceService` | 同上 | 幂等启动、`/health` 轮询、记录 PID 与归属、停止/重启 |
| `IVoiceServiceProcess` | 同上 | 进程接缝；真实实现包 `System.Diagnostics.Process`，测试用假实现 |
| `CompanionWindow` | 现有 | 启动时拉起、退出时收走 |
| `CompanionVoiceUi` | 现有 | 解释器输入框、重启按钮、状态文案；检测/试听前先保证服务在跑 |

### 脚本与端口

| 引擎 | 脚本 | 默认端口 |
| --- | --- | --- |
| `f5` | `tts_server.py` | 8765 |
| `kokoro` | `tts_kokoro_server.py` | 8766 |
| `gsv` | `tts_gsv_server.py` | 8767 |
| `system` | 无 | 无 |

端口从接口地址取，所以自定义端口照样能拉起。命令行固定为 `<脚本> --host 127.0.0.1 --port <端口>`，工作目录是语音文件夹（脚本按 `models\<engine>` 找权重）。启动前调用一次 `CompanionVoicePacks.ExtractScripts()`，脚本缺了就从嵌入资源补上。

### 解释器解析顺序

1. 设置里的「Python 解释器」（相对路径按语音文件夹解析；只写 `python` 这类名字时交给 PATH）
2. `<语音文件夹>\.venv\Scripts\python.exe`
3. `<语音文件夹>\venv\Scripts\python.exe`
4. `<语音文件夹>\python.exe`
5. PATH 里的 `python`

### 外部服务

启动前先探测 `/health`（2 秒超时）。已在应答就不启动，标记为外部，退出时不杀。这样开发机上手动常驻的服务不会被程序抢端口，也不会被程序误杀。

### 诊断

新增 `VoiceServiceStarted` / `VoiceServiceStopped` / `VoiceServiceFailed` 三个事件，`kind=voice`，`directory` 指向语音文件夹；进程日志只保留最后 8 行，失败时随诊断记录，避免管道写满卡死子进程。

## 设置页

语音页新增：

- 「Python 解释器」文本框，占位说明留空时的查找顺序；改动即时保存。
- 「重启服务」按钮：先停再起，用于换了解释器之后。
- 状态行改为四种：`服务由程序启动（PID 1234）`、`外部服务已连接`、`启动中…`、`启动失败：<原因>`。
- 「语音模型」每行的启动提示从「启动：python tts_server.py」改成「由程序自动启动」。

## 偏好

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `SpeechAutoStart` | `true` | 关闭后退回纯手动：不启动也不停止 |
| `SpeechPython` | `""` | 解释器路径；空白按上面的顺序自动找 |

两者加入 `CompanionPreferences.Read` 的归一化和诊断的 `settingNames`。

## 测试

`AnimationUiVerification --speech-audio` 增加约 10 项，用假进程和假探针，不依赖 python 与显卡：

- 引擎→脚本/端口映射；`system`、非本机地址、自动启动关闭时都不启动。
- 解释器解析顺序与相对路径解析。
- 命令行包含 `--host 127.0.0.1 --port <端口>`。
- 已应答时走「外部」，不启动进程。
- 同一份服务重复调用只启动一次。
- 停止只杀自己拉起的进程，外部服务不动。
- 启动失败的进程归为失败状态。
- `SpeechPython` 归一化。

## 非目标

- 不自动安装 python、不建 venv、不下载 pip 依赖（沿用语音页说明）。
- 不改三个合成脚本的行为，不加父进程看门狗：程序被强杀的情况下残留进程仍可能出现，但正常退出一定收走。
- 不做跨机器/远程服务托管：非本机地址一律只连不管。
